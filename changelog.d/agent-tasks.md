- Reasoning sessions and an agent task API. A session keeps the work around one question (its subject, notes, links to the recommendations, events, entities, signals and reasoning runs it touched, and its tasks) in Postgres, so it picks up after a restart; `POST /v1/sessions` and the routes under it open, note, link, close and reopen one. An outside agent or the Brain Console queues a task for a session at `POST /v1/tasks`, claims it (`POST /v1/tasks/claim` or `/v1/tasks/:id/claim`) under a lease that runs out (300 seconds by default, renewed by progress), and either has the instance run it (`/run`) or reports its own result (`/complete`). The allowed kinds are the instance's existing read-only operations (reason, ask, brief, verify, value, feedback, signals, recommendations), checked when the task is made; any other kind is turned down, no kind writes to a vendor, and writes still go only through the WriteGate. Sessions and tasks take idempotency keys, a lease that runs out puts the task back in the queue for the next agent and turns the old lease down, three claims without finishing fail it, and every change is kept in the append-only `work_audit` table, written in the same statement as the change. All routes need the instance key; the support key gets 403. See docs/sessions-and-tasks.md.
- The routes' read-only operations are shared between each route and its task kind (`brainOperations`), so both answer with the same checks.
