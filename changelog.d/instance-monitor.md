- Instance monitor (`npm run monitor`): checks each client instance's `GET /healthz` and `GET /v1/support/status` with its support key only, and reports when an instance doesn't answer or answers with anything but 200, an enabled connector's last sync failed, its last success is older than a threshold (24 hours by default) or it is missing settings, dead letters pass a threshold or grow since the last check, migrations are missing, or scheduled reasoning fails several runs in a row or goes without a success for three intervals. A config file or `MONITOR_CONFIG` lists each instance's name, base URL and the name of the variable holding its key, never the key; a field that looks like a key is turned down. Each request has a timeout and one retry after a network error, follows no redirect and sends the key only to the status route. The report and its JSON show scheme and host only, keep only the fields the rules read, and replace every key used with `[redacted]`. Exits 0 when healthy, 1 when something needs attention, 2 when it can't run.
- A reusable `Instance monitor` workflow (`workflow_call` and `workflow_dispatch`, no schedule) for a private ops repo to run on its own schedule with its own secrets: it masks each key, keeps counts between runs in the Actions cache, and with `open-issues` keeps one issue per instance in the calling repo with only `issues: write`, commenting when what's wrong changes and closing it when the instance is healthy again. See [monitoring instances](docs/monitoring.md).
